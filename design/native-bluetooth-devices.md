# Shared Bluetooth devices

Status: implemented candidate, 2026-11-04. The interactive [480px prototype](bluetooth-devices.html) uses simulated records; firmware displays only owner observations. This user revision supersedes separate input-host and audio pairing navigation, while retaining independent transport and permission ownership.

System Bluetooth settings opens **Bluetooth devices**, preselected to **Mouse & Keyboard**. Audio's **Manage devices** opens the same panel at **Audio**. Two 224 × 48 purpose buttons remain at the top. Search name and actual pairing state precede four 456 × 44 saved-record rows and pagination. The input footer has Add device / Stop pairing / More; More retains Resume, confirmed Forget all and a link to the shared Settings > Device name page. The Audio footer has Add device / Stop pairing / Refresh. Audio keeps its USB/Bluetooth selection, actual host/status, Mic and Speaker controls. Its primary Manage devices action does not require opening connection settings first.

Rows preserve the owning transport's identity and revision. Matching names and addresses across purposes do not combine records or authority. LE uses its complete durable key and address type. Classic uses the owner's exact saved BR/EDR record and catalogue revision; pinned SDK exports no saved Classic names, so the real identity is displayed. Unknown is not an empty successful list.

Input Add reuses the native release/disconnect, durable policy and LE pairing workflow. Input selection explains that the host must initiate reconnect. Disconnect acts only on the verified current saved record and retains the pairing; exact single Forget retains its existing confirmation, deletion receipt and remaining-host verification. Audio Add reuses the reviewed Classic pairing owner and shared LE/Classic capacity reservation. It shows the actual Classic search name, discoverability, countdown and errors. Entering management, pairing or connecting service links never starts audio, changes HID/USB selection or sends the keyboard draft.

Audio record details expose separate Mic and Speaker connection requests where the owner permits them. Each binds the exact selected saved record, Classic catalogue, shared and profile generation; actual connection events and request results determine state. A service connection is not active capture/playback. Active audio, pending commands and privacy/resource barriers can require stopping Mic/Speaker first. Different active peers must disconnect before connecting another saved device.

Connect mic reuses the existing SLC-to-SCO sequence, including an already connected SLC. The detail distinguishes service connection from voice connection; neither grants microphone capture. Each pending device-management phase retains its exact owner receipt. The coordinator binds that receipt revocation to the HID engine cancellation callback, before automatic cancellation advances the input epoch. The existing page, lock and access boundaries revoke only that receipt synchronously before an epoch, page, lock or maintenance transition; this does not wait for the next media poll. The existing BT lock orders revocation against the final dispatch claim: revocation that wins prevents SDK submission, while an already won claim is not retroactively withdrawn. The serialized Classic dispatcher also rechecks the other service's actual host before connecting, so an intervening foreign HFP/A2DP callback cannot authorize a cross-host request.

During first-boot browsing, both purposes permit read-only paging and entering/returning from details. Typed navigation is admitted separately from pairing, connection, preference, deletion and name changes. Full maintenance pause still blocks navigation. Classic catalogue refresh or failure retains the last successful rows and selected record identity, with independently observed link state. Retained rows remain browsable but cannot authorize a link action. The page reports checking or unknown saved state alongside the pairing-window state; only a complete catalogue can establish that a record is no longer saved. Refresh requests a read through the existing Classic owner, without pairing or discoverability changes. It is available during read-only browsing when audio is stopped and no pairing, link request or refresh is pending.

Connect requests reuse saved audio pairings. If the host asks to pair, return to the Audio device list, choose Add device, confirm locally, then use the displayed search name in the host's Bluetooth settings while Mosaico is discoverable. Connect actions are disabled during this pairing flow. The detail provides that recovery path after a matching saved Connect fails or becomes unconfirmed. The list gives active pairing status precedence over older link results.

Classic single Forget is **unavailable** in this candidate. The pinned GAP removal API posts an address-only removal; BTU memory deletion and later BTC durable-key deletion cannot currently be constrained by one immutable record token. The existing owner has no verified deletion transaction that preserves a replacement bond and cross-transport state throughout these phases. No SDK removal is submitted and no successful deletion is shown. The UI explains whether input state is unknown or the same address is also saved for input, and offers Disconnect while retaining pairing. Forgetting on Windows does not delete the Mosaico record; a future safe owner capability can replace this disabled action.

The coordinator supplies an explicit Audio-management context only inside these panels and their local pairing confirmation, allowing Mouse, Keyboard and Audio entry without pretending the foreground mode changed. Confirmation uses the existing post-open epoch binding. Leaving, locking, losing authorization or replacing the actual host invalidates stale requests. Existing BLE and Classic owners retain their admission, cleanup, capacity and callback contracts; no parallel connection manager is introduced.

Acceptance includes empty/unknown and saved lists, same display name in both purposes, link loss and replacement, held presses and catalogue changes, purpose switching, confirmation cancellation and return to the original mode. Native LVGL renders in both themes and the real coordinator/media/connection tests are required. Radio interoperability, physical display and acoustic results remain device evidence.
