# Input validation coverage

Scope: Mouse/Keyboard/Audio, Bluetooth/USB input, settings and their safety boundaries, reviewed 2026-10-21. The browser prototype defines the original interaction intent; the later [focused mode workspace revision](requirements.md#focused-mode-workspace-revision) explicitly replaces persistent navigation with core controls and an on-demand menu. A diagnostic transport screen alone does not satisfy P0. Product acceptance remains defined in [requirements](requirements.md), [interaction](interaction.md) and [validation](validation.md), with the explicit later revision governing changed navigation. This matrix separates executable evidence from planned checks; it does not assign a coverage percentage.

## Combined source delivery coverage

The current aggregate runner includes portable input, multitouch, the single board
touch reader, BLE/USB HID, BT/UAC audio, codec/display/recording HALs, settings,
Wi-Fi profiles, presentation, boot UI, audio engine/store, spoken letters, media
runtime/controls, typed control protocol, command bridge, remote input/device/media,
restart worker, trust/clock/update runtime and native connection controls. Tests
exercise production code with explicit SDK boundaries; accepted requests and
asynchronous acknowledgements remain distinct. The separate native LVGL suite
checks actual rendering, coordinate hits, immutable review identity and bounded
navigation/idle memory. Current delivery results belong in [validation](validation.md);
the numbered checkpoints below retain historical evidence.

The deferred device matrix covers physical IMU/touch accuracy, RF coexistence,
real host enumeration and audio, storage power interruption, partition migration,
OTA rollback and sustained powered operation. No host test substitutes for those
results, and no physical device is accessed during the source-only delivery.

## Evidence levels and commands

- **Host-tested:** portable production code, production adapter code with substituted SDK boundaries, descriptor bytes or offline capture tooling passed an executable check. This does not prove real SDK callbacks, radio delivery or target UI effects.
- **Source-reviewed:** an owning implementation was inspected. This is weaker than an executable failure-path check.
- **Target-compiled:** the exact firmware tree built with recorded SDK/BSP revisions, target and configuration. Compilation does not establish pairing or compatibility.
- **Device-tested / host-compatible:** an actual board and named host/OS passed the recorded procedure. Every device check below is pending until a device evidence record exists.

Run portable behavior tests with `python3 tools/check.py` and the independent report-map check with `python3 tests/test_hid_contract.py`. The standalone HID engine regression command is also documented in the [engine guide](../components/hid_engine/README.md#host-regression-command). Run `python3 tools/check_repository.py` for first-party text and local links. Target build instructions and dependency pins belong in the [firmware guide](../firmware/README.md); these commands do not flash a device.

`tests/test_hid_contract.py` compiles a read-only probe of the production descriptor, then decodes HID items independently. Expected report IDs, lengths, usages and bit offsets are fixed in the test rather than imported from production macros. It fails on missing sources/compiler, malformed items or a contract mismatch. Its small decoder is deliberately scoped to this report map, not a general HID conformance tool.

The complete runner also executes the [BLE adapter harness](../tests/ble_hid/README.md), [production coordinator harness](../tests/coordinator/README.md), [board adapter harness](../tests/board_port/README.md) and [offline serial-capture tests](../tests/test_device_smoke.py). The adapter harness compiles production `ble_hid.c` with substituted Bluetooth, NVS, clock, task and queue boundaries. The coordinator harness includes production `main.c` and links the real interaction model, engine and core, substituting only its SDK, board, UI and transport boundaries. The board harness compiles production `board_mosaico.c` with controlled BSP, driver, task and clock boundaries. These prove software behavior within their models, not encryption enforcement, RTOS scheduling or physical radio/sensor/flash behavior.

Run the separate [native LVGL UI suite](../tests/ui/README.md) with `python3 tests/ui/run.py` after resolving the locked firmware dependencies. It compiles unchanged production `app_ui.c` with managed LVGL 9.5.0, RGB565 FULL rendering and the firmware's Montserrat fonts. Its pointer driver performs real LVGL coordinate hit testing and records emitted intents; it does not reconstruct the UI in a browser or acknowledge actions on the coordinator's behalf. Address/undefined-behavior sanitizers instrument both the UI and LVGL. The focused-workspace checkpoint below passes both native suites and renders 174 PNGs across Light and Dark, retaining all 164 prior scenario names. The earlier 34/36-image runs and `.agent/local/ui-nine-transport/validation-manifest.json` are historical layouts. PNG review and physical-display validation remain separate from successful event assertions.

## Status, settings and display lifecycle regressions

The expanded scope adds battery/power, Wi-Fi and BLE status, pairing controls, persistent settings and automatic screen-off. The idle default is **5 minutes**, with **1 / 5 / 10 / 30 minutes / Off** choices. The production interfaces are now available and the coordinator harness links the real `device_settings` policy. The matrix below remains an acceptance and ownership checklist; a listed scenario does not itself establish a passing result. Existing session-only appearance and unavailable-status evidence does not qualify the expanded behavior.

The harness substitutes clocks, board power/brightness, network/BLE adapters and the settings-store boundary. It records ordered HID submissions, display requests, connection operations, settings requests and rendered snapshots so a safe final state cannot hide an earlier unwanted action. The separate [production settings-store harness](../tests/settings_store/README.md) tests actual NVS set/commit decisions with storage and RTOS boundary doubles. All credentials and peer data are synthetic; neither harness opens a serial port, manipulates a device, accesses a real network or erases actual bonds/settings.

## Focused workspace host evidence and target memory acceptance

The focused UI has a stable native checkpoint in `.agent/local/ui-product-final-stable/validation-manifest.json`: both suites passed, all 174 PNG hashes were verified, and all 164 prior scenario names remain. Independent reconciliation matched every production UI and test input to the current tree. The separate `.agent/local/ui-focused-final-01/` run passed both executables but changed production source during execution; its `source_stable=false` result remains nonfinal. The resource observer delegates every allocation to the unchanged LVGL CLIB backend. With FULL rendering, RGB565, 15 ms refresh and 60 DPI, all **50** settled cases passed: each feeds 100 snapshots over 10 simulated seconds and records **zero allocations, reallocations, frees, flushes and flush bytes**. Coverage includes identical primary/panel state, hidden About/bond changes, screen-off and target-name changes behind Settings Home in both themes. The visible-change positive control produced one full-frame flush. These measurements distinguish render calls from actual flush callbacks; they do not measure physical LCD transfers, dirty-area internals or frame timing.

Each theme also passed **1,000 open/close cycles across 17 panel variants** on the same UI instance after warm-up. Every close restored 102 core objects, two timers, 1,021 live blocks and 43,357 requested live bytes; the observed panel peak was 142 objects and the requested-memory peak was 58,865 bytes. Both remain within the approved 102 core / 160 panel ceilings. Teardown retained zero tracked blocks and bytes. The observer excludes allocator overhead and test framebuffers; it does not establish target internal/DMA headroom or PSRAM savings. Long-label and 32-entry bond rendering are separate visual cases; the repeated resource workload uses 15 synthetic saved hosts. Repeated theme switching, allocation-failure injection and target first-open latency are not established by this loop.

Retained regressions exposed repeated allocation/flushes from ellipsized-label comparisons, covered-shell updates, lost terminal touch events when setup expiry disabled a held control, and a missing connection-error detail when release was pending. The owning UI implementation was corrected; the checks now pass without dropping scenarios or weakening idle/gesture requirements. Earlier screenshots and failed measurements remain historical evidence, not relabeled final results.

The recorded expanded device baseline is **failed**. `.agent/local/device-smoke-expanded-baseline.json` contains five health samples over a 46.918-second incomplete capture requested for 90 seconds. Internal free memory ranged from **2,991 to 12,435 bytes**, and the largest internal block from **864 to 8,192 bytes**, despite total free heap exceeding 14 MB. Its paired raw log records repeated LCD `ESP_ERR_NO_MEM` errors. Bluetooth reported failure; the capture also ended with serial/framing errors. These observations establish low internal-memory headroom during that run, not the precise failing allocation's capability/size or proof that every failure shares one cause. Preserve the failed evidence and identify the replacement build separately in [validation](validation.md).

## Wire contract

Payload lengths exclude the transport Report ID. The report map describes the following bit layout; BLE Report Reference and characteristic wiring must agree with it. This is a Report Protocol device; an 8-byte keyboard payload alone does not establish Boot Protocol support.

| ID / direction | Byte layout | Independent check |
| --- | --- | --- |
| 1 / input | Byte 0: modifiers E0..E7; byte 1: constant zero/reserved; bytes 2..7: six Keyboard-page usages | 64 report bits, modifiers Data/Variable/Absolute, keys Data/Array/Absolute |
| 1 / output | Bits 0..4: Num Lock, Caps Lock, Scroll Lock, Compose, Kana; bits 5..7: constant padding | 8 report bits, LED-page usages 1..5, logical 0..1 |
| 2 / input | Byte 0: buttons 1..3 and five padding bits; bytes 1..3: X, Y, wheel | 32 report bits, axes Data/Variable/Relative with logical -127..127 |

The parser follows the item-state and report definitions in [USB HID 1.11, sections 6.2.2 and 8](https://www.usb.org/sites/default/files/hid1_11.pdf). BLE characteristic behavior requires separate checks against the [HID over GATT profile](https://www.bluetooth.com/specifications/specs/hid-over-gatt-profile-1-0/). Neither reference nor this test constitutes Bluetooth qualification.

[HOGP 1.0, section 3 and Table 3.1](https://www.bluetooth.org/docman/handlers/downloaddoc.ashx?doc_id=245141) requires Device Information and Battery services alongside HID; section 3.3.2 requires the PnP ID characteristic. Parsing a valid HID Report Map does not check these services, device identity or battery measurements.

[Bluetooth Core 6.2, GATT section 3.3.3.3](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/Core-62/out/en/host/generic-attribute-profile--gatt-.html) requires bonded clients' CCCD values to persist across connections. Subscription restoration must be keyed to the verified peer; it must never restore a queued input action or bypass encryption.

## Bounded serial health capture

[tools/device_smoke.py](../tools/device_smoke.py) provides a read-only, bounded capture after the device owner has completed deployment and released the serial port. Run `python3 tools/device_smoke.py --port PORT --seconds 90 --output .agent/local/device-smoke-RUN`, replacing `PORT` and `RUN` explicitly. The default duration is 90 seconds; the minimum is 35. `pyserial` is imported only for live capture. The tool sets DTR and RTS inactive before opening and transmits no data. It does not flash or request a reset; driver/device behavior on opening still requires actual device observation.

Passing requires a completed capture, at least three valid health samples, strictly increasing firmware uptime, queue occupancy <=32, and no ESP error, panic, watchdog, boot-fault or brownout evidence. Initial, intermediate and final health silence must each stay within 25 seconds against the production 10-second cadence. Freshness uses monotonic host arrival times rather than firmware uptime; a final partial line retains its actual arrival time. A line already started at the deadline has a fixed one-second grace to reach its newline; duration includes grace, all fault/size/freshness checks remain active and an unfinished line still fails. Optional BLE status must be boolean; reported initialization or transport failure fails capture, while a healthy disconnected device is allowed. A serial failure, malformed health line, oversized line or log beyond 1 MiB fails the capture. The retained raw log is capped at 1 MiB and the partial-line buffer at 8 KiB; only fixed-size aggregate health state is retained in addition.

The output prefix produces `.log` and `.json` files and refuses to overwrite existing evidence. JSON contains numeric duration, sample timing, memory/stack ranges, queue observations and fixed failure codes; it excludes port identity and raw messages. Absent optional measurements remain absent. The raw log stays local and may contain device details. Twenty-three offline tests cover valid/fragmented logs, missing evidence, reset/duplicate uptime, fault families, overflow/bounds, fake serial disconnect, inactive control lines, initial/final/intermediate silence, the 25-second boundary, deadline-cut framing and optional BLE status. Two added cases verify fragmented optional DMA measurements, independent observed ranges, and absent/partial/zero values without inventing missing fields. These parser checks do not impose or qualify memory-headroom thresholds. These tests never import pyserial or open a device. Neither an offline pass nor a successful live capture qualifies host input, memory-leak absence or long-duration operation.
