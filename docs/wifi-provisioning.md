# Basic Wi-Fi setup service

Status: service implemented and boundary-tested, 2026-10-21; integration and device acceptance are separate. Basic Wi-Fi provisioning, saved-network reconnect and RSSI belong to the current settings phase. Remote HID and MCP remain future work under the [remote-control design](remote-control.md).

## Integration contract

The new [app_wifi API](../firmware/main/app_wifi.h) is separate from device UI, the coordinator, board adapters and BLE. Startup calls `app_wifi_init()` once after shared NVS initialization. It owns Wi-Fi/default STA and AP netifs and a low-priority worker; it never erases the shared NVS partition or initializes Bluetooth. The coordinator admits local settings actions with `app_wifi_start_setup()`, `app_wifi_stop_setup()` and `app_wifi_forget_network()`, then polls `app_wifi_get_snapshot()` for actual completion. An `ESP_OK` action return means accepted, not connected, saved or stopped.

The public snapshot contains no credential/token: initialization/configuration, connection state, SSID, IPv4 address, valid RSSI in dBm, disconnect reason, retry countdown, pending-operation flag, last operation error and separate connection, cleanup and storage errors. `app_wifi_init()` returns worker admission; `initialized` and the error fields report actual SDK/storage initialization. `app_wifi_get_setup_info()` is a separate trusted local-display API for the temporary AP password. The caller must clear that copy after closing the setup screen or expiry and must not log it. The service does not draw UI or change HID ownership.

`configured` and `ssid` describe the selected runtime station configuration. Durable storage is independent: `stored_data_known` says whether record presence is known, `stored_data_present` is meaningful only when known, and `stored_ssid` is empty unless the stored record was successfully saved/read and valid. A corrupt record can be known-present without a usable SSID. `storage_uncertain` and `storage_error` remain visible after a failed storage operation even if setup closes or the radio reconnects successfully. Only a successful explicit save/forget or read verification resolves that uncertainty. `app_wifi_verify_storage()` performs a bounded read and updates this metadata without switching the runtime network.

The UI must allow explicit forget/recovery when `configured` is false but a record is present, storage is uncertain, or its presence is unknown. Gate the action on service readiness and operation availability, not `configured` alone. Never invent an SSID to enable recovery. Show runtime and remembered-network state separately when they differ. While `cleanup_pending` is true, show stopping/retrying plus `cleanup_error` and `cleanup_retry_in_ms`; do not show an active password or offer a new setup session. `setup_active` can remain true during cleanup because an HTTP/AP resource is not yet confirmed stopped; it does not mean portal admission is enabled.

Setup is explicitly local and never starts automatically at boot or on connection failure. It opens a ten-minute, WPA2-protected SoftAP with a new random password and token each time. A phone/computer joins that AP and opens its displayed IPv4 URL. The small local form accepts one network name and WPA2 passphrase. It uses bounded request/form sizes, a session token, exact Host/Origin checks, HTML escaping and an AP-interface-bound HTTP listener. It exposes no input, shell, arbitrary settings, firmware update or remote-control API.

This is a physically initiated temporary provisioning portal, not a production LAN control server. HTTP has no application TLS inside the WPA2 setup network. Anyone given its AP password can open its form, so show it only to the local person and stop it promptly. WPA2 credentials are the initial supported station mode; open/WEP/enterprise and browser-based hidden-network scanning are not implied. The user types the SSID directly.

Credentials use one versioned NVS blob and Wi-Fi driver RAM storage. Development flash/NVS is not encrypted by this service; physical flash access can recover credentials. Credential buffers are cleared after parsing/copying, never echoed in HTML or logs, and excluded from snapshots. This does not guarantee scrubbing inside the SDK driver, HTTP socket or browser. Production flash/NVS encryption and provisioning TLS are separate release work.

Integration must add `app_wifi.c` and SDK component requirements `esp_wifi`, `esp_netif`, `esp_event`, `esp_http_server`, `esp_timer`, `nvs_flash` and the normal FreeRTOS support. Keep the pinned SDK's software Wi-Fi/Bluetooth coexistence enabled; do not reinitialize the Bluetooth controller. Actual radio coexistence, portal phone/browser compatibility, RSSI and power behavior require device testing. No flash or deployment is part of this change.

## Bounds and failure behavior

- One low-priority worker, one pending credential slot and coalesced local control flags; stop/forget invalidate queued submissions before the next worker step. They do not interrupt an NVS operation already in progress or undo an applied write. Forget is a separate erase, and never erases Bluetooth bonds or the whole NVS partition.
- Poll interval 200 ms; connection attempt timeout 15 seconds; retry delays 1, 2, 4, 8, 16 and then at most 30 seconds. Retries continue at the capped interval without allocating more jobs. Connection success resets backoff. Failure never opens an AP automatically.
- AP password is 24 random hex characters; form token is an independent 128-bit value. One setup client, two HTTP sockets, two routes, 512-byte encoded body, 32-byte SSID and 8..63 printable ASCII passphrase. UTF-8 SSIDs are validated. Reject unsupported/oversized input without truncation. No station network scan is exposed.
- Portal binds the AP netif with the pinned HTTP server's `if_name` API and also checks exact AP-IP Host and Origin. It serves only `/` and POST `/configure`; unknown routes do not gain access to other firmware functionality. No captive DNS, arbitrary CORS or automatic phone portal detection is promised. Open the displayed URL explicitly.
- Each form is single-use, protected by a token and the current generation/deadline. HTTP 202 means admitted, not saved or connected. NVS set/erase errors do not guarantee rollback: flash may contain the previous record, the replacement record or no record even when an error is returned. The service keeps its previous runtime network on a failed save/forget, marks stored contents unknown and uncertain, and requires explicit successful save/forget/read verification to reconcile them. Reboot may read a different stored network or no network; it does not replay a queued command. A corrupt/unreadable record reports storage status while retaining local setup/forget recovery.
- Setup expires after ten minutes, or closes five seconds after the submitted network actually connects. Local stop immediately invalidates admission; its worker then stops the HTTP server and restores STA-only mode. The HTTP task has two-second socket waits; a fragmented body has an additional four-second overall read budget. Shutdown may wait for a bounded in-flight socket operation and is not a HID callback.
- Stop, expiry and failed-start cleanup immediately revoke admission and clear locally held setup secrets. HTTP shutdown and AP-to-STA transitions are tracked independently. If either SDK operation fails, keep `cleanup_pending`, `setup_active` and `operation_pending` true, retain its cleanup error and retry only outstanding cleanup work no more than once per 1,000 ms after the previous attempt completes, subject to the 200 ms worker poll. Repeated local stop requests cannot create a hot retry loop. Continue until both operations acknowledge completion; never reopen setup automatically. No valid token survives stop, and credential retrieval is unavailable throughout cleanup. Actual radio shutdown still needs device acceptance.
- A failed forget does not claim credentials were erased or preserved. Its runtime configuration and uncertain storage are reported separately. Invalid RSSI is explicitly marked invalid; empty IP outside Connected means unavailable, not a successful zero address. Connected means current association plus assigned IPv4, not Internet reachability.
- Application credential buffers are cleared after use. SDK/browser/socket copies and physical flash erasure are outside that guarantee. No secret appears in service-generated logs, snapshots or responses. Only the locally rendered setup page contains its own session token; it never echoes either the AP password or submitted station passphrase.

The pinned [NVS API implementation](https://github.com/espressif/esp-idf/blob/383dda6c182e3dabf6355160166fe007df775629/components/nvs_flash/src/nvs_api.cpp) and [simple handle implementation](https://github.com/espressif/esp-idf/blob/383dda6c182e3dabf6355160166fe007df775629/components/nvs_flash/src/nvs_handle_simple.cpp) write in set/erase; commit is a no-op for a valid handle in this revision. Tests model those direct writes and both unchanged/already-applied error outcomes. They do not model a rollback transaction or infer physical power-loss durability from a return code.

`python3 tests/wifi/run.py` passes production-service boundary tests under address/undefined sanitizers, plus explicit unsupported-hardware behavior. `python3 tests/wifi/compile_target.py` passes S31 object compilation against the pinned SDK and current build configuration. See [test coverage and device gates](../tests/wifi/README.md). These results do not establish final linked integration, an actual AP/browser connection, flash persistence on hardware or BLE coexistence.
